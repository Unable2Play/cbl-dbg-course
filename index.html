01

One Word Changes Everything

What cbl-gdb does, and what really happens when you type cobcd instead of cobc.

Your program gets translated behind your back

COBOL is the language behind most of the world's banks and payrolls. GnuCOBOL is a free compiler for it, and it has a quirk: it never turns your COBOL straight into a program. It first translates it into C, and lets a C compiler finish the job.

1

prog.cbl
The COBOL you wrote

→
2

prog.c
C that no human wrote

→
3

prog
The runnable program

That is fine until something goes wrong and you open a debugger. The standard one, GDB, only sees step 2. It shows you the machine-written C, not your COBOL.

What you wrote

10 datyr PIC 9(4).

A four-digit year, called datyr.

What GDB sees

b_15 + 17

Four bytes, starting 17 bytes into a blob called b_15.

🎬
Think of it like a dubbed film

You wrote the script in one language. The film was dubbed into another, and the only transcript the projectionist has is the dubbed one. cbl-gdb adds subtitles in your original language.

The fix is one extra letter

You do not learn a new workflow. Wherever you would have typed cobc, you type cobcd (the "d" is for debugging). Then you open the result in GDB as usual.

Before 
# ordinary compile
cobc -x prog.cbl
After 
# debuggable compile
cobcd -x prog.cbl
gdb ./prog

Inside GDB you now have new commands that understand COBOL names. This is real output from the project's own test suite, after typing cprint * ("show me every variable"):

GDB 
(gdb) cprint/v0 *
12 : 01 PEANUTS  : ' ' <repeats 63 times>, "123456789"
13 : 02 FILLER/PEANUTS  : ' ' <repeats 63 times>
14 : 02 NAME-FIRST/PEANUTS  : 123.456789

Line 14 is the point. In memory that value is just the characters 123456789. The debugger put the decimal point in the right place because it knows how the COBOL declared that field.

Your new vocabulary inside GDB

cbl-gdb adds a family of commands, all starting with "c" for COBOL. These six cover most of a debugging session.

🔎

cprint

Show a variable by its COBOL name. cprint VAR="x" changes it.

✋

cbreak

Set a breakpoint on a line, a section, or a whole program.

👁️

cwatch

Set a watchpoint: pause the instant a variable changes.

⏭️

cnext

Step to the next COBOL line, stepping over a PERFORM instead of diving into it.

🧭

cbacktrace

A backtrace with the non-COBOL plumbing filtered out.

▶️

cstart

(Re)start the program and stop at the first COBOL statement.

COBOL in thirty seconds

You will see COBOL snippets throughout this course. Here is one paragraph from the sample program that ships with cbl-gdb. It reads records from one file, fixes a date, and writes them to another.

optfde01.cbl 
       02-process.          MOVE input-record TO oeit.          PERFORM 50-fix-date.          MOVE oeit TO output-record.          WRITE output-record.          ADD 1 TO custmas-ctr.
PLAIN ENGLISH

This is a named block of steps called "02-process". COBOL calls it a paragraph.

Copy the line we just read from the file into a working area called oeit.

Go run the "50-fix-date" paragraph, then come back here.

Copy the fixed-up working area into the outgoing record.

Write that record to the output file.

Count it: add one to the "records modified" counter.

When you pause on that last line, the natural question is "what is custmas-ctr right now?" Everything cbl-gdb does exists so that cprint custmas-ctr can answer it.

What happened in the second after you pressed Enter

cobcd looks like a compiler, but it is a wrapper: it hands the real work to other tools and slips in two extra steps of its own. The rest of this course unpacks this list.

1
cobcd asks the real compiler for its plan

It runs cobc in a "tell me what you would do, but don't do it" mode.

2
COBOL becomes C

GnuCOBOL does its usual translation and leaves notes about every variable in the C file.

3
Extra step: a who's-who list is stapled on

A helper reads those notes and appends a compact table of every COBOL variable to the C file.

4
Extra step: the line numbers are corrected

A second helper edits the half-compiled program so "line 42" means line 42 of your .cbl, not of the C.

5
The program is finished as normal

The result runs exactly like an ordinary build. It just carries extra luggage.

6
Later, GDB opens the luggage

When you debug, GDB loads a Python script that reads the who's-who list and provides cprint and friends.

💡
Key insight: wrap it, don't rewrite it

cbl-gdb never changes GnuCOBOL or GDB. It wraps one and plugs into the other. When you ask an AI to add a capability to a tool you don't own, "wrap it" or "write a plugin for it" is usually the safer request than "modify it".

Meet the Cast

Five small programs, four borrowed tools, and exactly who is responsible for what.

A crew of specialists

cbl-gdb is not one program. It is run like a heist crew: one planner who talks to the client, and a handful of specialists who each do a single job well and never meet the client at all.

🎩
cobcd, the Planner

The only one you ever type. A Python script that decides the order of work, calls everyone else, and cleans up afterwards.

🗺️
cobcd-st, the Cartographer

"st" is for symbol table. Reads the generated C and draws the map of every COBOL variable: name, location, size, type.

✂️
cobcd-sfix, the Editor

"sfix" means "fix the .s file". It edits the assembly so every instruction is credited to a line of your COBOL rather than a line of C.

🗣️
cobcd.py, the Interpreter

About 8,400 lines of Python that live inside GDB during a debug session. It provides cprint, cbreak, cwatch and the rest.

🚪
cobcd-rw, the Bouncer

"rw" is for reserved words. Hand it a few lines of COBOL and it turns away every word that belongs to the language, leaving only possible variable names.

The Road Trip from COBOL to Machine

How the build-time crew passes your program along, and the two detours cbl-gdb adds to the route.

Four towns between your code and a running program

A build is a road trip with fixed stops. Each stop is a file in a different format, a little closer to what the chip understands. Normally cobc drives the whole way without stopping and throws away the in-between files.

1

prog.cbl
Source code

→
2

prog.c
Generated C

→
3

prog.s
Assembly

→
4

prog.o
Object file

→
5

prog
Executable

cbl-gdb needs to get out of the car twice: once at town 2 to add something to the C, and once at town 3 to edit the assembly. The problem is that cobc is the one driving.

Ask for the directions, then drive yourself

The Planner's solution is neat. It asks cobc to do the first leg (COBOL to C) and then, instead of continuing, to print out the commands it would have run next. The Planner then runs those commands itself, with its two detours added.

cobcd 
        os.environ["COBC_GEN_DUMP_COMMENTS"]= '1'        TRIPLE_X_ADDITION = " -### -save-temps -A -ggdb -fgen-c-line-directives -fgen-c-labels "        TRIPLE_X_COMMAND = DeSpace(COBC + TRIPLE_X_ADDITION) + COMMAND_LINE
PLAIN ENGLISH

Flip a setting that tells GnuCOBOL: "while you write the C, leave a note for every COBOL variable."

Prepare a handful of extra instructions to give to cobc (decoded below).

The final command is: cobc, plus our extras, plus everything the user originally typed.

Each of those extras is a flag. Here is what the Planner is really asking for:

-### Don't run the C compiler. Just print the commands you would have run. This is a dry run.
-save-temps Don't delete the in-between files. We need to open them.
-A -ggdb Pass "-ggdb" along to the C compiler: include full information for the debugger.
-fgen-c-line-directives In the generated C, mark which COBOL line each chunk came from.
-fgen-c-labels In the generated C, add named signposts for COBOL sections and paragraphs.

Reading the directions

What comes back from cobc is a plain block of text. The Planner reads it line by line and reacts to three kinds of line.

preprocessing:

Note the file names. Nothing to do yet.

translating:

A C file now exists. Detour 1: send it to cobcd-st.

to be executed:

A command cobc held back. Run it in two halves, with Detour 2 (cobcd-sfix) in the middle.

cobcd 
        test_for = "translating:"        n = line.find(test_for)        if n == 0 :            we_translated_something = True            tokens = line.split()            i_file = tokens[1]            c_file = tokens[3]            cbl_file = tokens[4].replace('(','').replace(')','')            to_be_deleted.append(c_file)            to_be_deleted.append(i_file)
PLAIN ENGLISH

We are looking for a line that starts with the word "translating:".

Where in this line does that word appear?

If it is right at the start (position 0), this is one of ours.

Make a note that real work happened, so we know to tidy up later.

Chop the line into separate words.

The 2nd word is the pre-processed COBOL file.

The 4th word is the C file that was just created.

The 5th word, minus its brackets, is the original COBOL file.

Put both in-between files on the "delete when finished" list.

⚠️
Reading another program's chatter is fragile

This only works while cobc keeps printing exactly these words in exactly this order. The author knew it: just before this, the script forces the language to English so the messages can't arrive in German. If an AI proposes parsing a tool's human-readable output, ask whether the tool offers a structured format instead.

Detour 1: what the Cartographer leaves behind

cobcd-st boils every COBOL variable down to one short record and joins them into a single enormous piece of text. Think of a spreadsheet squashed onto one line: a | between columns and a ~ at the end of each row.

variables.cpp 
    ss << variable->record_type             << "|" ;    ss << ZeroIsNull(variable->level)       << "|" ;    ss << name                              << "|" ;    ss << variable->f_name                  << "|" ;    ss << (variable->b_name EQ "cob_local_ptr" ? "" : variable->b_name) << "|" ;    ss << variable->a_name                  << "|" ;    ss << ZeroIsNull(variable->offset)      << "|" ;    ss << variable->length                  << "|" ;    ss << ZeroIsNull(variable->occurs_min)  << "|" ;
PLAIN ENGLISH

Write which part of the program it belongs to (W for WORKING-STORAGE, L for LOCAL-STORAGE...), then a bar.

Write its COBOL level number (01, 05, 10...). If it's zero, write nothing.

Write its COBOL name.

Write the name of its descriptor in the C code, if it has one.

Write the name of the block of memory that holds it.

Write the name of its "type card": is it text, a number, how many digits?

Write how far into that block of memory it starts.

Write how many bytes long it is.

If it repeats (a table), write the minimum number of repeats.

So the datyr field from Module 1 ends up as a record shaped roughly like this (reconstructed from an example in the project's comments):

W|10|datyr||b_15|a_7|17|4|||~

"In WORKING-STORAGE, level 10, named datyr, held in block b_15, type card a_7, starts 17 bytes in, 4 bytes long." That text is written into the C file as an ordinary piece of data, so it gets compiled into your program.

💡
Key insight: pack the map inside the suitcase

The variable table could have been a separate file sitting next to the program. Embedding it means it can never be lost, left behind when the program is copied to another machine, or be out of date. When two things must always match, shipping them as one thing removes a whole class of bugs.

Detour 2: what the Editor cuts

Assembly files contain little notes that say "the following instructions came from file N, line L". GDB uses them to know which source line to show you. Because your program went through C, the notes point at two kinds of file, and GDB gets confused about which to display.

Before sfix 
# illustrative
.loc 3 1412 5   # prog.c
.loc 1 110 11   # prog.cbl
.loc 4 88 3     # prog.c.h
After sfix 
# illustrative

.loc 1 110 11   # prog.cbl

cobcd-sfix first makes a list of every file the assembly mentions and gives each a verdict: zero means "pretend this never existed".

sfix.cpp 
        if( filename EQ params.c_filename ) {            // Skip over the cobc-generated .c file            retval[it->second] = 0;            continue;        }        if( filename.substr(filename.length()-2) EQ ".h"                OR filename.substr(filename.length()-2) EQ ".c") {            // Skip over any xxxx.h file            retval[it->second] = 0;            continue;        }        if( filename EQ params.cbl_filename ) {            // Force the COBOL source file to be #1            retval[it->second] = 1;            continue;        }
PLAIN ENGLISH

If this is the C file that GnuCOBOL generated...

...give it a zero ("ignore") and move on to the next file.

If the file name ends in ".h" or ".c", it is some other piece of C plumbing...

...zero for that one too.

If this is the COBOL file the user actually wrote...

...mark it as a keeper.

(This author writes EQ and OR instead of == and ||. A personal habit, not standard C++.)

Then it copies the assembly out line by line. Any line note whose file got a zero is simply not copied. With only COBOL notes left, GDB has no choice but to show you COBOL.

Inside the Debugger

The build is over. Now follow cprint custmas-ctr from your keyboard to an answer.

First problem: GDB has never heard of cobcd.py

GDB only gains COBOL powers if it loads the Interpreter script. Nobody wants to do that by hand each time, so the Planner leaves GDB a hint at build time. Which kind of hint is called the FMODE, and there are five choices:

0 Leave no hint at all. You load the script yourself.
1 The default. Write the script's name into a special section of the program. GDB reads it and goes looking for cobcd.py.
2 Write the entire script into the program. All 8,400 lines travel inside it.
3 Put a symlink called prog-gdb.py next to the program. GDB automatically loads a file with that name.
4 Put a full copy of the script, named prog-gdb.py, next to the program.

Why so many? Because no single method works everywhere, as this piece of the Planner admits:

cobcd 
    if windows :        ## In Windows attempting to embed either the filename or the file fails.        ## And we can't create a symlink because we don't have admin privileges        FMODE = COBCDFMODE or "4"  ## We will create make a renamed copy of cobcd.py next to the executable
PLAIN ENGLISH

If we are running on Windows...

...options 1 and 2 don't work there.

...and option 3 needs administrator rights we don't have.

So unless the user insists otherwise, fall back to option 4: a plain copy.

🔒
The most common "it doesn't work"

GDB refuses to auto-load scripts from folders it has not been told to trust. If cprint is an "undefined command", the build is probably fine and the script just was not loaded. The install step prints the lines to add to your ~/.gdbinit settings file, starting with add-auto-load-safe-path.

How a script teaches GDB a new word

GDB offers a plugin API: hand it a small bundle that says "my name is X, and here is what to do when someone types X", and X becomes a real command. Here is the simplest command in the project, complete.

cobcd.py 
  def __init__(self):    if GV_noisy_registration:      print('Registering command help-cobol')    super(CHelp, self).__init__("help-cobol", gdb.COMMAND_USER)   def invoke(self, arguments, from_tty):    try:      print(self.CHELP_TEXT)    except KeyboardInterrupt as ki:      print(ki)
PLAIN ENGLISH

Part one, "set up": this runs once, when the script is loaded.

If we are in chatty mode, announce ourselves.

The important line: tell GDB "I am a command, and my name is help-cobol".

Part two, "invoke": GDB runs this every time someone types the command.

Print the help text.

If the user presses Ctrl-C part-way through, don't crash. Just stop politely.

Every c-command follows this two-part shape. At the very bottom of the script, one line per command switches them all on:

cobcd.py 
CPrint()
CWatch()
CBreak()
CLoad()
CNext()
💡
Key insight: look for the extension points

Before asking an AI to build a feature into a tool, ask it: "does this tool have a plugin or extension API?" GDB, VS Code, browsers, Blender and most serious tools do. Building on the official hook means your work survives the tool's next update.

Unpacking the catalog

This is the "cut it at every ~ and every |" moment in real code. It is the mirror image of the C++ you read in Module 3, which wrote those same bars and squiggles.

cobcd.py 
    variable_lines = variable_string.split('~')    for variable_line in variable_lines:      tokens = variable_line.split('|')      self.line_list.LoadFromLine(tokens)      self.var_trie.LoadTrieFromLine(tokens)      self.LoadPerformFromLine(tokens)
PLAIN ENGLISH

Cut the giant text at every ~ to get one record per row.

For each of those rows...

...cut it at every | to get its separate columns.

If the row describes where a program starts, remember that line number.

If the row describes a variable, file it in the name index (a trie).

If the row describes a PERFORM, remember where it returns to. cnext uses this to step over it.

🤝
Key insight: a data format is a contract

The writer is C++ and runs at build time. The reader is Python and runs days later. All they share is an agreement: ten columns, in this order, split by these symbols. The Python even finds columns by position number. If you ask an AI to change one side, tell it explicitly to update the other side too.

Bytes are not numbers until someone reads them

The shelf holds raw bytes. What they mean depends on the type card, because COBOL can store the same number in very different ways. Here is 12345, three times:

As text (DISPLAY)

31 32 33 34 35

One byte per digit, 5 bytes. Readable, bulky.

Packed (COMP-3)

12 34 5C

Two digits per byte, with the sign tucked into the last half-byte. 3 bytes.

Binary (COMP)

30 39

The way the chip itself counts. 2 bytes.

The Interpreter has a small decoder for each. This is the heart of the packed one. A nybble is half a byte.

cobcd.py 
  for digit in digits:    nybble = digit >> 4    if nybble == 0x0B or nybble == 0x0D:      is_negative = True    elif nybble <= 0x09:      value *= 10      value += nybble    nybble = digit & 0x0F    if nybble == 0x0B or nybble == 0x0D:      is_negative = True    elif nybble <= 0x09:      value *= 10      value += nybble
PLAIN ENGLISH

Take the bytes one at a time.

Look at the left half of this byte.

If it is the special code B or D, that is a minus sign. Remember the number is negative.

If it is 0 to 9, it is a real digit: shift what we have one place left and add it on. (12 becomes 120, plus 3, is 123.)

Now look at the right half of the same byte...

...and do exactly the same two checks again.

Anything else (like the C in 5C, meaning "plus") is quietly skipped.

Don't do the same work twice (but know when to redo it)

Reading and filing a whole catalog is slow for big programs. A comment in the code records a test with 30,000 variables: the catalog was 1.7 million characters and took over a second to file. Nobody wants that pause on every command.

🗄️

Keep what you filed

Once a catalog is parsed, the result is stashed under the catalog's name. Come back to that program later and it is ready instantly. This is a cache.

🚩

Distrust what you fetched

Values read from memory are also remembered. But the moment the program runs again they may be wrong, so every one is flagged "dirty" and re-read on next use.

The second card is three lines of code. GDB announces "the program just stopped" as an event, and the Interpreter has signed up to hear it:

When Things Break

How this project fails safely, remembers its scars, and checks its own work. The habits that separate a demo from a tool people rely on.

Fail like an escalator

When an escalator breaks, it becomes stairs. It is worse, but you still get upstairs. When a lift breaks, you are stuck. The Planner is built like an escalator: if its clever route fails for any reason, it quietly does what you would have done without it.

PLAIN ENGLISH

If the "print me your plan" request blew up, for whatever reason...

...don't try to diagnose it. It is usually a typo in a file name or a mistake in the COBOL.

Rebuild the exact command the user would have typed without us: plain cobc.

Say out loud that we are falling back, and show the command.

Run it. The user sees the real compiler's own, familiar error messages.

The technical name is graceful degradation. Notice what it buys: a COBOL typo produces a COBOL error message, not a confusing complaint from deep inside cbl-gdb. The fallback also passes the failure signal along (its return code), so anything automating the build still knows it failed.

Doing it twice should be the same as doing it once

The Cartographer staples a variable table onto the end of the C file. What if it gets run on the same file twice? Two tables, a broken build. So before stapling, it checks for its own earlier work.

If we reach a line that is our own signature...

(Afterwards the kept lines are written back, followed by one fresh table.)

💡
Key insight: idempotent means "safe to repeat"

A pedestrian-crossing button is idempotent: pressing it five times is the same as pressing it once. Any step that modifies a file, sends a message or charges a card should be built this way, because sooner or later it will run twice. It is a word worth using with your AI: "make this step idempotent".

Turning the lights on

The Planner "works pretty hard at being invisible", as its own comments put it. That is lovely until something goes wrong. So every crew member has a switch that makes it narrate what it is doing. Each is an environment variable you put in front of the command.

ECHO=1 Print every command the Planner runs, in order. (Adding -v does the same.)
COBCDNOCLEAN=1 Don't delete the in-between files. Leave the .c and .s where you can open them.
